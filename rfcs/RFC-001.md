# Guided Code Review Skill

## Problem Statement

As our team adopts agentic development, the sheer number of PRs to review has grown too large to handle.

## Solution

We need a code review skill which performs a first pass and then guides a human through the PR. This skill should:

1. Run an initial evaluation of the PR against our coding charters and mandates
2. Explain what the PR is doing to the human reviewer
3. Highlight any initial issues that violate the coding charters, and ask the human reviewer if they'd like to add comments for those
4. Make an initial decision as to whether the agent could approve the PR as-is, or if there are additional areas of investigation for a human to dig into
5. If there are areas to dig deeper on, the agent should present these areas interactively to the reviewer in the chat session, explaining the issues, what to look into, and offering some options. The reviewer should then be able to provide feedback right within the session
6. Once the process is complete, the agent should offer to create a review in a pending state so that the human reviewer can go in and tweak the comments / approve / request changes / etc.

## Background

The coding charter that lives in docs/coding-charter is more focused on new code written by our software factory. The area that will fail most commonly is the task tracking identifiers leaking into code. We shouldn't pursue those unless there is literally only 1 instance of it in the entire PR. Otherwise, we should use that charter as a guide for what "really good" code looks like, so we should call out the most egregious violations. The user should be given the choice to include those issues in the review, or ignore them. Oftentimes there may be more pressing issues that we want addressed, not diluted by a bunch of (valid) nitpicks.

## Technical Notes

- We should be using the gh CLI for now, eventually we'll create a review command in the flight-rules CLI
- The review should consider the coding charters, but also be a holistic review. Look for security issues, code smells, logical errors, sloppy code, etc. Someone could write code that perfectly complies with the charter, but is otherwise a dumpster fire

## Known Gaps and Edge Cases

- We should be aware of stacked PRs, that is something our team does a lot of. When you see a stacked PR, you should consider the downstream changes, but try and focus explicitly on the changes unique to that PR
- No multi-repo PRs
- If the PR is so big that it blows up the context, we should just request a smaller PR
