# Execute-work skill: agent-driven ticket implementation

## Problem Statement

The flight-rules skill set has grown to cover the planning portion of software development very well, but there is nothing to support the actual execution of tickets themselves. This means that we lose grounding in things such as our coding charter once engineers enter the implementation phase.

## Solution

We need a targeted "execute-work" skill which leverages a model-bound agent to write and verify code. This skill should:

- read the relevant task from whatever configured tracker is set up for the project
- build context and a prompt around a given task, as well as any supporting details from the current environment — including references to relevant RFCs, TDDs, and other task-tracking materials in the initial agent input, when relevant
- delegate implementation of the task to a lower-intelligence model (something like Sonnet), via the agent
- delegate verification of the task to a lower-intelligence model, via another agent. This agent should be provided with just the acceptance criteria and asked to verify each of them. It can be provided other output as well, but the primary response should be itemized details from the acceptance criteria
- iterate in a loop (3 max iterations) where the implementation agent writes code and the verification agent verifies it. If it's unverified, the implementation agent is given details as to what's wrong and takes another pass. If it fails verification after the 3rd attempt, we bail out to the user
- include references to the Coding Charter in both the implementation and verification agents' system prompts
- empower both agents to respond with a request for user feedback if something is truly ambiguous or unsuccessful — given the lower-tier models, we don't want them guessing

## Background

We've written lots of specs with this skill so far, but the execution falls flat because it has no context from our broader system. For example, most PRs we put up would be rejected by our guided-code-review skill, as they deviate from the charter and include little-to-no domain-driven design. While we will eventually automate the code review process with an "autonomous" variant, we should still ensure that the output of our first-pass implementation is at least cognizant of these requirements.

## Technical Notes

We should expand the CLI as relevant. I want this to interact with the broader system, for example:

- We should use the git commit command from the CLI to generate deterministic commits. I don't want the auto-generated Claude Code commits
- We should create a template for the proper pull request. We can work on this interactively, but it should be defined as a Zod schema which then helps populate the actual pull request itself, similar to what we do with the git commit command from the CLI
- We should also move the relevant tickets through the system as they're worked. They should be set to in-progress when the implementation agent starts work. When the PR is up, they should be moved to in-review
- We should also fetch ticket details and other task-tracker data through the CLI, rather than having agents hit trackers directly
