# Claude Agent SDK runtime and the Hopper review-remediation bot

## Problem Statement

When a comprehensive code review leaves charter-grounded findings on a PR, nothing remediates them with the PR's intent in hand: the existing comment-addressing bot sees only the review threads, not the PR description or the flight-rules ticket behind it, and fixes outside flight-rules' verified fix loop.

## Solution

Add a Claude Agent SDK binding to flight-rules alongside the Deep Agents one. Build Hopper, a manually summoned GitHub Action in tlp-actions, on top of it. Hopper is named after Grace Hopper.

In Seth's words (2026-11-02):

> I'd be interested to see if we could create a github action similar to the comment-addresser and test-remediation, that is powered by flight-rules behind the scenes. The thought is simple: it would be used in repos that already leverage code-review in comprehensive mode, so the review comments are based on the coding charters. I'd want the agent bot to ground itself in the pr description _as well as_ the referenced jira ticket which would be in the flight-rules format. This would allow the bot to better understand the intent of the pr and how best to remediate the comments. It would then use any relevant flight-rules skills (maybe even the commit and comment publishing logic?) to make fixes in that branch, commit them, and then respond to any relevant comments. It should be scoped to only prs where it has been summoned, so I'd want it triggered off of a comment like /hopper-remediate. If this worked, we would eventually have it run automatically, but I want to keep it manual for now.

What gets built:

- **`./sdk/claude-agent`** (flight-rules): a worker runtime and skill runtime over `@anthropic-ai/claude-agent-sdk` with the same contract as `./sdk/deepagents`.
- **PR review-thread operations** (flight-rules): read a PR's review threads, and reply inside an existing thread.
- **`remediate-review` skill** (flight-rules): execute-work's private-review remediation phase (step 8), run against an existing PR and its open review threads instead of a review the skill produced itself.
- **Hopper** (tlp-actions): a `/hopper-remediate` comment trigger that runs `remediate-review` through the Claude Agent SDK runtime on the PR's branch.

## Background

- RFC-006 E6 (#171) shipped the neutral `./sdk`, the MCP server and the Deep Agents binding. It explicitly deferred "GitHub mentions/webhooks, a deployed conversation service … and ThinkLP infrastructure" to a later product epic. Hopper is that product, run as a CI job rather than a service.
- tlp-actions' `claude-code-review` already pins flight-rules and, in comprehensive mode, applies the autonomous review method with the coding charters. Each finding is posted with a flight-rules `<!-- code-review:finding … -->` marker, and its state is reconciled by `review-state` on the next pass.
- tlp-actions' `claude-comment-addressing` and `claude-test-remediation` reusable workflows run `claude-code-action` with a prompt. They have no ticket grounding, no verifier gate and no shared triage vocabulary with the reviewer.
- execute-work (1.94.3, #285) already triages review findings through code-verifier, runs one bounded `VerifiedImplementationLoop` remediation pass, and replies only in other reviewers' existing threads. Hopper reuses that behavior; it does not redesign it.

## Technical Notes

### Claude Agent SDK binding (flight-rules)

- Same public shape as `./sdk/deepagents`: `ClaudeAgentWorkerRuntime({ agents, models, toolGrants, observe })` and `ClaudeAgentSkillRuntime`. A registration picks its model tier at construction, and dispatch cannot override it. Tiers come from the Claude adapter's `model-tiers.json`.
- Workers get canonical prompts from `instructionCatalog`, not from loading the native Claude plugin. Tool grants stay adapter-enforced in one place: each grant maps to `AgentDefinition.tools`/`disallowedTools`, and a `canUseTool` guard rejects any call outside the observed grant before it runs. Read-only registrations never receive write, shell or task tools.
- Run with `settingSources: []` so the repository's or runner's Claude settings, hooks and plugins cannot widen a worker's access.
- Shared flight-rules operations reach the model as an in-process MCP server (`createSdkMcpServer`). The same launch-bound operation registry and permissions apply as for the MCP adapter. No handler shells out to the CLI.
- Final reports pass through the existing role/mode report codec. Only a valid YAML report becomes a completed outcome.
- Human questions map to an SDK session pause and `resume`. Hopper runs with `allowHumanQuestions: false`, so anything needing a human becomes an escalation reply, never a default answer.
- `@anthropic-ai/claude-agent-sdk` is an optional peer with an exact dev/test pin, isolated like the LangChain peers. Root, `./review` and `./sdk` consumers must not load it.
- Deterministic CI stubs the SDK's `query` stream to check grant mapping, the call guard, report validation and cancellation. A live-provider test is reported separately and is not required for CI.

### Review-thread operations (flight-rules)

- `pr-threads`: returns the PR header (title, body, branch, head SHA) and its review threads with id, path, line, outdated/resolved state, author, author type and body. A flight-rules finding marker is parsed only from a thread's root comment, and only when its author is on a caller-supplied trusted list, so a commenter cannot forge a finding.
- `pr-thread-reply`: posts a reply in an existing thread.
- No resolve operation. Closing a finding belongs to its reviewer: the code-review bot reconciles on its next pass, and humans resolve their own threads. This matches execute-work step 8c.

### `remediate-review` skill (flight-rules)

1. Resolve the ticket from the PR title (`type(KEY): …`), branch or body, and read it through the tracker operations. If there is no ticket, or it isn't in the layered flight-rules format, ground in the PR description alone and say so in the summary.
2. Collect open, unresolved, non-outdated threads, both reviewer findings and human comments.
3. code-verifier triages each one with its existing triage outcomes (`fix`, `ignore` with evidence, `needs_input`), grounded in the ticket, the PR intent and the charters.
4. Run one bounded remediation pass (at most three attempts) for accepted fixes. The verifier rechecks the original acceptance criteria plus every accepted fix before anything is committed.
5. Commit and push with the existing git operations, after reconciling the PR head; an unexpected new commit stops the run.
6. Reply in each thread:
   - `fix`: the commit SHA and the evidence
   - `ignore`: an explanation grounded in the ticket, the intent and the triage evidence
   - `needs_input`: escalate to a human with the open question, never guess
7. Post one summary comment.

execute-work step 8 and `remediate-review` share the triage/remediate/reply procedure from one source so the two cannot drift.

### Hopper (tlp-actions)

- A reusable workflow plus a Node action, modeled on `claude-code-review` (package-pinned flight-rules, App token, OTEL export).
- Trigger: an `issue_comment` on a PR whose body starts with `/hopper-remediate`, from a user with write access. It acks with a 👀 reaction and serializes per PR without cancelling an in-flight run. Fork PRs are refused.
- Identity: commits and replies use the existing `thinklp-claude-automations` App, and replies are signed as Hopper. A dedicated Hopper App is deferred.
- Jira credentials are passed so the ticket read works. The FRT ticket is the expected grounding source.
- `claude-comment-addressing` must ignore comments starting with `/hopper`. Otherwise both bots run on the same comment and push to the same branch.

## Known Gaps and Edge Cases

- **Loops.** A Hopper push can re-trigger the code review, which can post new findings. While Hopper stays manual this cannot loop, but making it automatic needs a round cap like comment-addressing's.
- **Concurrent pushes.** The author or another bot can push mid-run. Head reconciliation stops the run instead of force-pushing or verifying stale code.
- **Outdated threads.** Threads on lines that no longer exist are skipped and listed in the summary.
- **Decide findings.** Product or design calls are escalated with the options stated. Hopper never picks one.
- **Cost.** Each run is bounded by the three-attempt remediation cap and a max-turns input. A PR with many findings may be only partly remediated, and the summary says which threads remain.
- **Out of scope:** automatic triggering, resolving threads, non-GitHub hosts, a hosted (non-CI) Hopper service, and replacing `claude-comment-addressing`. Replacement is a follow-up once Hopper proves itself.

## Epic Sketch

- **E1 · Claude Agent SDK runtime and review remediation** (flight-rules, GitHub issues): `./sdk/claude-agent` worker runtime; skill runtime; `pr-threads`/`pr-thread-reply` operations; `remediate-review` skill with execute-work step 8 extracted to a shared reference; installed-consumer proof.
- **E2 · Hopper action** (tlp-actions, Jira FRT): `hopper-remediate` reusable workflow and action on the E1 release; `/hopper` exclusion in comment-addressing; example caller and pilot in one repo that runs comprehensive review.

E2 starts after E1 is released.

## Definition of Success

- On a pilot PR with comprehensive-review findings, one `/hopper-remediate` comment produces verified fix commits and a reply in every addressed thread. The reviewer's next pass marks those findings fixed.
- Replies are grounded in the ticket's intent, so the author never has to restate what the PR is for.
- No unverified change is pushed, and no decide finding is settled by the bot.
- Hopper is trusted enough that the follow-up conversation is whether to run it automatically, not whether it works.
