# QA lane with visual evidence

## Problem Statement

Nothing in the pipeline shows that the work behaves correctly in the running product, so bugs go unreproduced, fixes go unverified, and reviewers take the agent's word for it.

## Solution

Add a QA lane to flight-rules beside the implement and review lanes, so every bug is reproduced with evidence, every ticket is verified with evidence, and every PR with a visible consequence ships with evidence a human can look at.

- Port the `repro-and-document` and `verify-fix` skills from `think-lp/agentic-skills` into flight-rules. Jira evidence uses native attachments. GitHub PR evidence uses `gh --attach`. The GCS bucket goes away.
- Extract the generic "drive a web client, capture screenshots and video" flow into a standalone `capture-evidence` skill that the repro skill, the verify skill, and `execute-work` all call.
- Add a `qa-engineer` agent that reproduces bugs into concise steps to reproduce, and verifies both bug and story work when a ticket reaches the QA column. It reads both the bug-report format and the layered-body format.
- Put visual evidence into all three pipeline steps: reproduction, verification, and `execute-work`'s ship step, which attaches what it captured to the PR and the ticket.
- Define a standardized Bug Report body format, a sibling of the layered-body format: human-readable content at the top, expandable agent content beneath, with explicit Fixed When criteria.
- Teach `execute-work` to read both formats and work against either.

On when to capture, in the author's words:

> It doesn't always have to, especially if it's an API-only change. But if there is a visual change that could be reviewed, we should generate something. This would even extend to something like "This API endpoint returns a string in a new format, so we screenshot the web."

## Background

`repro-and-document` and `verify-fix` exist today as two SKILL.md files and three Python scripts in the `thinklp` plugin. They reproduce bugs against ThinkLP staging with `playwright-cli`, record one-take 1080p video, attach evidence to Jira natively, and label the ticket with an `Agentic-Reproduction-*` or `Agentic-Verification-*` outcome. They work, but they are ThinkLP-specific, they prompt for credentials on every run, they read tickets through the Atlassian MCP, and they push GitHub-facing evidence to a public GCS bucket because GitHub had no CLI upload.

Two things changed. GitHub CLI 2.99.0 (2026-09-01) added a repeatable `--attach` flag to `gh issue|pr create|edit|comment` that uploads images and video and rewrites body references in place, which removes the need for the bucket. And flight-rules now has the pieces the skills were improvising: a ticket CLI, a layered body format with parsers, an `execute-work` orchestrator with a verifier, and a tech-writer agent authoring PR bodies with an `OTS Material` slot built for exactly this evidence.

Direction decisions from the author, verbatim:

> We're moving away from the "github-as-a-tracker" concept, so we'll be a jira only house.

> We should massively improve the MarkdownADF parser so that we can support better formatted comments and post bodies across jira. Remember, humans are reading this, not robots. It needs to be visually appealing.

> Every step in the pipeline should reduce the amount of information and unknowns that the next agent deals with.

## Technical Notes

- **Jira is the only tracker.** GitHub tracker methods added by this work throw `NotImplemented`. PRs still land on GitHub through `gh`.
- **All Atlassian MCP calls move into the flight-rules CLI.** `ticket get` gains `attachments`, `reporter`, and `issueType`.
- **Markdown ⇄ ADF is rebuilt on a real AST** (`remark` + `mdast`), covering GFM tables, nested lists, blockquotes, images, and GitHub admonitions mapped to ADF panels. Round-trip fidelity is tested with golden files. In the author's words: "Go ahead and make a proper AST, it's important. I think that's crucial to making this work well in Markdown and Jira."
- **Evidence attaches with gh's model everywhere.** `--attach <file>#<caption>` on `ticket comment`, `ticket edit`, `pr create`, and a new `pr comment`. A `![alt](./file)` reference in the body is rewritten to the uploaded media; unreferenced files append. One `EvidenceService` underneath. No standalone upload verb.
- **`pr create` moves from Octokit to `gh`** so `--attach` is reachable. The `PullRequestHost` interface is unchanged.
- **Labels and comments get CLI commands:** `ticket label --add/--remove`, `ticket comment --body-file`.
- **Credentials: one env contract, two providers.** `capture-evidence` reads `FLIGHT_RULES_QA_USERNAME` and `FLIGHT_RULES_QA_PASSWORD`. Either the operator exports them, or the QA recipe carries `op://` references that `op read` resolves at start. The future orchestrator uses `OP_SERVICE_ACCOUNT_TOKEN`. Nothing ever prompts.
- **Everything ThinkLP-specific becomes a QA recipe** at `.claude/flight-rules.qa.md` in the app repo: base URLs, login flow, token mint, data-setup helpers, known traps, credential references. The `thinklp` plugin shrinks to that file.
- **Format detection is issue-type first.** Jira `Bug` reads as a bug report; everything else reads as a layered body. `metadata.kind` overrides; heading sniff is the last fallback. The section reader sits behind a `SectionSource` interface so a later move to per-section Jira custom fields is an adapter swap.
- **`flight-rules check` gains a tools group:** `playwright-cli`, `ffmpeg`, `curl`, `gh >= 2.99.0` with push access, and `op` when the recipe uses it.
- **Existing conventions hold.** Agents never write to the tracker, git, or PRs; skills do. `qa-engineer` runs opus in `reproduce` mode and sonnet in `verify` mode. `code-verifier` is unchanged. `src/` changes ship a rebuilt `bin/flight-rules.mjs`.
- **Open PRs to build on**, merge order #83 → #84 → #85 → #81: #83 (ADF links) and #84 (`ticket edit`) merge as-is; #85 (tech-writer PR bodies, draft) needs the evidence manifest wired into `OTS Material`; #81 (execute-wave) needs a rebase and a bundle rebuild, and shares `execute-work` step 7 with #85.

## Known Gaps and Edge Cases

- **Triggering is manual for now.** `reproduce-bug` and `verify-ticket` run per ticket. A `qa-sweep` over the QA column, or a Claude Agent SDK orchestrator, is a follow-up. The skills are designed headless so that wrapper stays thin.
- **Removing the GitHub tracker from `setup` is out of scope.** This work stubs, it does not delete.
- **Per-section Jira custom fields are a follow-up.** `FieldSectionSource` and the field-mapping config land when the Jira screens do.
- **A "visible surface" hint in `break-down-work` is a follow-up.** For now `execute-work` derives capture directions itself and records `No visual evidence: <reason>` when there is nothing to show.
- **The recipe lives in one repo.** For ThinkLP that is `lps-client`. Bugs in `lps-api` are reproduced through the web client.
- **`gh --attach` needs push access** on the token, and on partial upload failure the PR is still created with a non-zero exit. Skills must read the printed URL, not the exit code.
- **Tooling is assumed installed.** `check` reports what is missing; nothing installs `playwright-cli` or `ffmpeg`.
- **Evidence size.** Video is 1080p `.webm`; Jira and GitHub attachment limits apply. The recipe sets a recording ceiling.

## Epic Sketch

- **A1. Tracker primitives** — multipart Jira client, `addAttachment`, `ticket comment`, `ticket label`, `ticket get` additions, gh-based `PullRequestHost`, `--attach` on write commands, `check` tools group.
- **A2. Rendering** — markdown ⇄ ADF rebuilt on an AST, admonitions → panels, media emission, Bug Report format and `docs/bug-report-format.md`, `SectionSource` interface, issue-type format detection.
- **B. `capture-evidence`** — the generic web-client driver, the QA recipe format and `docs/qa-recipe-format.md`, credential resolution with env and 1Password.
- **C. QA agent and skills** — `qa-engineer` agent, `reproduce-bug`, `verify-ticket`, `docs/qa-charter.md`, agent registration. Depends on A1, A2, B.
- **D. `execute-work` integration** — reads both formats, derives capture directions, attaches evidence to the PR and the ticket, feeds the tech-writer. Depends on A1, A2, B, and #85.

A1, A2, and B run in parallel. C and D run in parallel after them. Then the `thinklp` plugin shrinks to its recipe and retires its two skills.

## Definition of Success

- A bug ticket reaches a human with steps to reproduce, a root cause, Fixed When criteria, and before/after evidence, without a human having reproduced it.
- A ticket that lands in the QA column gets a pass or fail with evidence before a human opens it, for bugs and stories alike.
- A PR with a visible change carries screenshots or video a reviewer can judge without pulling the branch, and a PR without one says so.
- Tickets and comments the factory writes to Jira read as if a person wrote them: tables, panels, inline media, no flattened text.
- The `thinklp` plugin is one recipe file, and nothing in flight-rules names ThinkLP.
