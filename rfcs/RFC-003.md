# Jira / Jira Product Discovery Task Tracker Backend

## Problem Statement

Our teams who use Jira and Jira Product Discovery are unable to use the Flight Rules skills as it only supports Github for Task Tracking

## Solution

We need to write a full implementation of the TaskTracker interface which supports Jira and Jira Product Discovery

- We should ensure that this is fully supported. Not just in the TaskTracker, but in everything else that the flight rules cli supports, such as the dependency planner

## Background

Github was a good starting point for building out our constructs, but the production teams at our company run on Jira. So we really need to have an equivalent, deeply supported implementation which runs on that infra

## Technical Notes

**Interface**

- Implement against the existing backend-agnostic `TaskTracker` interface (`src/tasks/task-tracker/task-tracker.ts`, 18 methods). A new `JiraTaskTracker` mirrors `GitHubTaskTracker` (~470 lines) as a sibling implementation. No interface reshaping — the abstraction is already clean and we write against it.

**Mapping contract**

- Epic → native Jira **Epic** issue type
- Ticket → native **Story / Bug** issue type
- Initiative → **JPD Idea**
- Epic ↔ Initiative → link the Jira epic to the JPD idea via the native **delivery** construct
- Metadata → rendered with **native Atlassian markup** (expand / collapse macros) rather than GitHub's YAML-in-HTML-`<details>` approach

**Auth & API** (open — not yet decided)

- Thin, hand-rolled REST wrapper over the relevant Jira Cloud REST + JPD APIs (no heavy SDK), following the Octokit-style pattern used by the GitHub backend
- **API token** for v1; env vars mirror the GitHub pattern (e.g. `JIRA_TOKEN`, `JIRA_HOST`) and wire into the check command's credential map (`src/cli.ts:9-11`)
- OAuth is desired if it can be achieved without standing up a hosted auth server (see Known Gaps)

**Backend selection**

- Default backend chosen in the **setup skill**, written to `.claude/flight-rules.local.md` (`tracker: jira`). The config schema already declares `jira` as a valid value (`src/config.ts:23`); `buildTracker()` currently throws on it (`src/cli.ts:20-38`)
- Plus a **top-level CLI override flag** that ignores config and forces the named tracker for a single invocation (new global option in `buildProgram()`)

**Dependency planner**

- The dependency planner is purely algorithmic and backend-agnostic — it consumes the `Epic.childIssues[]` shape (`{ id, status, blockedBy }`) that the tracker already fetched, and never calls the tracker directly. "Full support in the dependency planner" therefore means the Jira backend must return that same childIssue + blockedBy shape, after which the planner works unchanged.

## Known Gaps and Edge Cases

1. **TechnicalDesign (TDD) has no native Jira equivalent.** On GitHub a TDD is a Discussion; Jira has no discussion threads. Store the TDD as a **Confluence page** and add a link to it in the body of the ticket.
2. **The JPD "delivery" link.** "Delivery" is a native JPD construct that can link anything from Jira. The exact API and semantics for creating and reading these links must be confirmed **during the research phase**.
3. **Blocked-by / dependencies.** Use the standard Jira **"blocks" / "is blocked by"** issue link types.
4. **OAuth.** Pursue OAuth **only if it can be done without standing up a hosted auth server** — creating an OAuth app in Atlassian is acceptable. Feasibility to be confirmed in research; otherwise fall back to the API-token path.
5. **`getUsers()`.** Return the **assignable users that are visible** to the caller (the Jira equivalent of GitHub collaborators).

## Ticket Sketch

- **Jira REST client + auth** — thin hand-rolled wrapper over the Jira Cloud REST API; API-token auth wired to `JIRA_TOKEN` / `JIRA_HOST` and the check-command credential map. *(Comes first — everything depends on it.)*
- **OAuth flow** — spike plus implementation, only if research confirms it is feasible without a hosted auth server
- **Core CRUD** — `createEpic` / `getEpic`, `createTicket` / `getTicket`, `createInitiative` / `getInitiative` mapped to Jira Epic / Story·Bug / JPD Idea
- **Linking & dependencies** — `linkTicketToEpic`, `linkEpicToInitiative` (JPD delivery construct), `blockTicket` / `unblockTicket` via "blocks" / "is blocked by"
- **Metadata & comments** — `updateEpicMetadata` / `updateTicketMetadata` / `updateTddMetadata`, `addComment`, using native Atlassian expand macros
- **TDD via Confluence** — `createTechnicalDesign` / `getTechnicalDesign` create a Confluence page and link it in the ticket body
- **Users & health** — `getUsers()` (assignable, visible), `ping()`
- **Backend wiring** — `buildTracker()` dispatch for `jira`, setup-skill config write, and the top-level CLI `--tracker` override flag

*Ordering: the REST client + auth ticket lands first; the remainder can largely proceed in parallel.*
